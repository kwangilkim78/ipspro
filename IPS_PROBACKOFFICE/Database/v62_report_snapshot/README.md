# 백오피스 보고서 스냅샷 SQL — MySQL 8.0.33

> **도입 보류 — 2026-09-08 사용자 결정**
> 현재는 SQL과 설계만 보관합니다. 데이터 증가로 실제 조회 성능이 저하되면 다시 검토합니다.
> DB 설치·초기 적재·자동 갱신 활성화, 앱 조회 경로 전환, C# Worker 개발은 진행하지 않습니다.
> 아래 실행 절차는 재검토 시 참고용이며 현재 실행 지시가 아닙니다.

운영 DB에는 아직 적용하지 않았습니다. 2026-09-08에 읽기 전용으로 확인한
`ips_ew.v_trading_report_backoffice`의 39개 컬럼/타입을 기준으로 작성했습니다.
운영 system_time_zone=KST, 앱 세션 time_zone=SYSTEM, binlog_format=ROW도 확인했습니다.

## 실행 순서

SQL 편집기의 **스크립트 실행** 기능으로 파일 하나씩 실행합니다. DELIMITER를 지원하는
MySQL Workbench/DBeaver 등의 클라이언트를 사용하고 오류가 나면 즉시 중단하세요.
다른 작업을 COMMIT하지 않도록 별도 연결을 사용합니다.

1. `00_preflight_and_backup.sql`: 버전·권한·동명 객체 확인. 두 SHOW CREATE VIEW 결과를 파일로 보관.
2. `01_install.sql`: 최초 한 번만 실행. 테이블 3개, 조회 뷰 1개, 프로시저 2개 생성.
3. `02_initial_refresh.sql`: 한가한 시간에 초기 적재. SUCCESS, row_count 및 elapsed_seconds 확인.
4. `03_verify.sql`: actual_rows = row_count, stored_hash_errors = 0 확인.
   원본에 변경이 없는 시점이면 mismatched_row_count도 0이어야 합니다.
5. 필요할 때만 `04_enable_schedule_OPTIONAL.sql`: 15분 주기 갱신 시작.
   01~03만 실행하면 자동 작업은 시작하지 않습니다.

현재 앱 계정은 CREATE VIEW 권한이 없으므로 설치는 DB 관리 계정으로 실행해야 합니다.
설치 계정이 프로시저/뷰의 DEFINER가 됩니다. CREATE/INDEX/CREATE VIEW/CREATE ROUTINE 및
원본 SELECT 권한, 생성 객체에 대한 SELECT/INSERT/UPDATE/DELETE 권한을 유지해야 합니다.
호출 계정에는 EXECUTE, 자동 작업 생성에는 EVENT 권한이 필요합니다.
READ COMMITTED 적재를 위해 binlog_format=ROW를 확인하세요. 전역 DB 설정은 스크립트가 바꾸지 않습니다.
설치 도중 실패하면 이미 생성된 객체가 남을 수 있습니다. 00 결과와 오류를 확인하고,
재실행을 위해 기존 테이블을 임의로 삭제하지 마세요.

## 저장/갱신 동작

- 복잡한 원본 뷰를 한 번 전체 읽어 새 스냅샷을 작성합니다. 원본 테이블/뷰는 수정하지 않습니다.
- 자료가 모두 저장된 뒤 활성 스냅샷 번호를 트랜잭션으로 전환합니다.
- 실패하거나 원본이 0건이면 기존 결과를 유지하며 실패 원인을 기록합니다.
- 연결 단위 잠금으로 갱신/복원 중복 실행을 막습니다.
- 현재와 직전 성공 스냅샷 2개를 보존합니다. 갱신 중에는 최대 3세대와 undo/log 공간이 필요합니다.
- 재실행은 새 스냅샷을 만들 뿐 거래를 누적 중복 삽입하지 않습니다.
  원본 자체에 있는 동일 행은 그대로 보존하며 임의 중복 제거를 하지 않습니다.
- BOKId는 원본 값을 그대로 저장하고 고유키로 사용하지 않습니다.
- 원본 조회 시각과 앱 기준 KST 시각(+9시간)을 분리하고 날짜/기관 조회 인덱스를 둡니다.
  업무일은 화면의 08:00~익일06:00 등 기존 설정에 맞춰 조회합니다.
- 확인된 운영 세션은 SYSTEM, 서버 시간대는 KST입니다. 프로시저는 +09:00 세션에서 읽어
  현재 앱이 받는 TIMESTAMP 표시값 그대로 DATETIME으로 저장합니다.
  bo_executed_at_source는 물리 UTC라고 가정하지 않은 원본 조회값입니다.
  앱이 기존 Buy.created/Sell.created를 사용할 때는 기존처럼 한 번만 +9시간 처리합니다.

## 이번 버전의 범위와 후속 작업

**전체 스냅샷 방식이며 증분 갱신 구현은 아닙니다.** 주문 modified만으로는 fills 변경,
삭제·취소, 기관 정보나 수수료 규칙 변경을 모두 포착할 수 없어서 증분을 임의 구현하지 않았습니다.
전월 정정/삭제도 다음 전체 갱신에 반영됩니다. 비용을 측정한 뒤 변경 추적을 설계해야 합니다.
자동 갱신은 사용자 수와 관계없이 한 번 수행하지만 그 자체의 DB 비용은 발생합니다.
전체 원본이 크면 15분도 부담일 수 있으므로 먼저 수동 적재 시간을 확인하세요.

수수료는 원본 문자열 그대로 저장합니다. 스위치 수수료·면제·기관 통화 등 C#의 최종 계산을
복제하거나 확정한 테이블은 아닙니다. 이 규칙은 앱 수정 시 기존 로직을 그대로 재사용해야 합니다.
현재 기관/딜러 조회와 규칙 조회도 자동으로 사라지지 않습니다.

**실행만으로 앱 속도가 바뀌지 않습니다.** 다음 단계에서 TradeRepository 등의 조회를
`v_bo_report_trades`로 연결하고 기간 전체를 한 번 조회해 기관별로 나눠야 합니다.
기존 뷰명을 바꿔치기하는 DDL은 포함하지 않았습니다. BOK는 따로 검증 후 연결합니다.
엑셀 생성 CPU/메모리 부하는 이 DB 스크립트만으로 해결되지 않습니다.

전체저장은 같은 스냅샷으로 읽어야 합니다. 같은 연결의 REPEATABLE READ 읽기 전용
트랜잭션에서 데이터를 모두 받거나, 전체 데이터를 한 SELECT로 받은 후 파일별로 나눕니다.
별도 연결에서 snapshot_id만 기억하는 방식은 두 번 갱신 후 해당 세대가 삭제될 수 있어 부적절합니다.
화면에는 스냅샷 완료시각을 표시하고 인보이스 확정 전에 갱신 완료 여부를 확인해야 합니다.

## 중지와 복원

- `05_stop_schedule.sql`: 이 패키지의 이벤트만 제거. 진행 중 작업은 끝날 때까지 기다립니다.
- `06_restore_previous.sql`: 직전 성공 데이터로 전환. 최초 적재뿐이면 이전 세대가 없습니다.
- 원래 앱과 뷰는 변경하지 않았으므로 설치를 중단해도 기존 조회 경로는 그대로입니다.
- 원본/스냅샷 테이블을 삭제하는 제거 스크립트는 제공하지 않습니다.
- 운영 실패는 snapshot_runs의 FAILED/ABORTED, 오래된 완료시각으로 확인합니다.
  연결 종료/서버 재시작은 다음 갱신 때 기존 RUNNING을 ABORTED로 기록합니다.
  별도 알림 연동은 포함하지 않습니다.

## 검증 범위

운영 MySQL 버전과 원본 컬럼 타입·시간대·binlog 설정은 조회로 확인했습니다.
EXPLAIN은 앱 계정의 원본 테이블 권한 부족으로 실행되지 않았습니다. 원본 DB에 DDL/CALL을 실행하지 않았습니다.
스냅샷 SELECT는 MySQL에 LIMIT 0으로 실행해 원본 39개+메타정보 6개 컬럼과 계산식이
정상 해석되는 것을 확인했습니다. 저장 프로시저의 실제 생성·실행은 아직 검증하지 않았습니다.
실제 설치·적재·갱신/복원 검증은 00~03 실행 결과로 확인해야 합니다.
